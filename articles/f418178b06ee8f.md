こんにちは、スマートショッピングでエンジニア担当の金尾です。



## 分散データベースのメリットと課題
　マイクロサービスでは、サービスごとにデータベースを所有するのが一般的です。これによりスキーマ変更の影響範囲を限定され、各サービスが疎結合になります。この際、マイクロサービスはデータベースのAPIとして機能します。
　![](https://storage.googleapis.com/zenn-user-upload/d6babdab4762-20240228.png)
　一方で、各サービスにデータが分散することにより、「各サービスを横断してデータを利用したい場合どうするか」という新たな問題が発生します。モノリシックなデータベース運用ではJOINや集約といったRDSのクエリで行えていたものをアプリケーション側で別途サポートしなければなりません。またクライアント側で解決しようとした場合、各クライアント・各サービスが結合してしまいアーキテクチャの変更が困難になる、関係するサービスすべてにアクセスする必要がありリクエスト数が増大する、認証認可の管理が複雑になるなどの問題があります。

![](https://storage.googleapis.com/zenn-user-upload/5d796eaedad2-20240228.png)

## API Gateway

![](https://storage.googleapis.com/zenn-user-upload/2dfa8fddf5d5-20240228.png)

クライアントと各マイクロサービスの間にAPI Gatewayを設置します。

Gateway以降の実装については、大きく分けてAPIコンポジションとCQRSの２つが挙げられます。これらは一方を採用したとしても、クライアントからはAPIの背後に隠蔽されているシステム要件の変化によって柔軟に選択、切り替えができます。

## APIコンポジション

![](https://storage.googleapis.com/zenn-user-upload/ba7fd77f575d-20240228.png)

APIコンポジションパターンでは、API Gatewayが複数のサービスに対するクエリをまとめ、単一のクエリとしてクライアントに提供します。これにより、クライアントは複数のサービスと直接やり取りする代わりに、API Gatewayを通して必要な情報を得ることができます。
このアプローチは実装がシンプルになる反面、集計やソートなどの複雑なクエリを実行したい場合にデータセットをメモリ内で全件処理するケースが出てくる場合があります。また、内部問い合わせが多くなりがちなため、レイテンシが問題になりやすく、キャッシュや並列処理といったチューニングで対処する必要があります。

## CQRS 

![](https://storage.googleapis.com/zenn-user-upload/a9b45281ac3c-20240228.png)

CQRS（Command Query Responsibility Segregation）は、読み取り操作と書き込み操作を別々に処理するアーキテクチャパターンです。CQRSサービスは各サービスの更新（command）イベントをサブスクライブし、自身が持つクエリ用のデータストアに反映させます。
このアプローチはJOINやGROUP BYといったRDSの機能をそのまま使うことができます。また要件に応じてNoSQLやElasticsearchといった他のデータストアに切り替えることも可能になります。反面、実装が複雑になりやすく、結果整合性などの別のデメリットを許容する必要があります。
